# 第 01 课：项目全景与启动链

## 1. 这个项目到底是什么

这是一个“请假审批系统 + AI 助手”的本地单机原型。

- 后端：FastAPI + Uvicorn。
- 旧业务层：`server.py` 中的 `BaseHTTPRequestHandler`。
- 数据库：默认 SQLite，可通过环境变量切换到 MySQL。
- 前端：Vue 3 + Vue Router，无构建步骤。
- AI：OpenAI 兼容对话接口 + 可选 Embedding 接口 + 本地 n-gram 检索兜底。

它不是现代意义上的单一后端框架项目，而是“新 FastAPI 外壳 + 旧业务处理器”的混合体。理解这一点，是后面读所有路由的前提。

## 2. 启动链

```text
run.bat
  -> 指定 Python 解释器
  -> start_fastapi.py
  -> uvicorn.run("fastapi_app:app")
  -> 导入 fastapi_app.py
  -> lifespan 执行 legacy.init_db()
  -> 建立或升级数据库结构
  -> 写入演示账号、余额和申请
  -> 启动 HTTP 服务
```

关键文件与位置：

- `start_fastapi.py:8`：Uvicorn 启动参数。
- `fastapi_app.py:13`：FastAPI lifespan。
- `fastapi_app.py:18`：创建应用。
- `server.py:124`：数据库初始化与演示数据。
- `db.py:371`：SQLite/MySQL 建表与增量列迁移。

注意：`run.bat` 硬编码了同级的另一个项目虚拟环境：

```text
C:\Users\zwb\Desktop\请假系统\.venv-win\Scripts\python.exe
```

这意味着本项目目录级可移植性不足。换机器或移动目录后，最稳妥的启动方式是用本项目自己的虚拟环境：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe start_fastapi.py
```

## 3. 前端加载链

`static/index.html` 只加载以下业务脚本：

```text
core.js
components.js
dialogs.js
shell.js
pages-login.js
pages-employee.js
pages-approver.js
detail-only.js
ai.js
app.js
```

它没有加载：

```text
pages-attendance.js
pages-overtime.js
pages-stats.js
pages-employee-admin.js
```

因此后面四个文件属于“源码存在，但当前页面不可用”的模块。即使 `core.js` 的 `pageMeta` 写了对应标题，也不代表页面已经接线。

加载顺序也有依赖关系：

1. `core.js` 先创建 `window.VP`、全局状态和 API 封装。
2. 其他页面文件把组件注册到 `VP.components`。
3. `app.js` 最后读取 `VP.components` 创建路由和挂载应用。

任何页面脚本如果排在 `core.js` 之前，都会因为拿不到 `VP` 而失败。

## 4. 路由链

`static/vue/app.js` 使用 Hash 路由：

```text
#/login
#/detail?id=N
#/home
#/apply
#/profile
#/records
#/guide
#/notifications
#/requests/:id
#/admin
#/history
#/admin/requests/:id
#/history/requests/:id
#/adjustments
#/hr
#/delegation
```

登录守卫的逻辑：

1. 访问登录页直接放行。
2. 全局状态没有当前用户时，调用 `VP.loadSession()`。
3. 会话恢复失败则跳回登录页。
4. `/enter` 按角色分流：审批员去 `/admin`，员工去 `/home`。
5. 审批类页面要求 `role === "approver"`。
6. HR 页面要求 `isHrOrAdmin()`。

当前后端只返回数据库中的 `employee` 或 `approver` 角色，不返回 `is_admin`、`is_hr`、`job_level`。因此前端虽然写了管理员和 HR 判断，当前后端实际上无法产生这些身份。`#/hr` 因此不可达。

## 5. 后端请求链

FastAPI 中有两类路由：

### 第一类：AI 原生路由

例如：

```text
GET  /api/ai/status
POST /api/ai/qa
POST /api/ai/review
POST /api/ai/parse
POST /api/ai/review-request/{id}
POST /api/ai/review-batch
```

这些路由在 `fastapi_app.py` 中直接实现，通过 `_auth_user()` 校验 `session` Cookie。

### 第二类：旧业务兼容路由

`fastapi_app.py` 最后注册了：

```text
@app.api_route("/{path:path}", methods=["GET", "POST"])
```

AI 未匹配到的请求全部进入 `compatibility_route()`，然后由 `run_legacy()`：

1. 创建一个不绑定真实 socket 的 `legacy.Handler` 对象。
2. 注入 path、method、headers、body。
3. 把响应暂时写入 `BytesIO`。
4. 调用旧 `do_GET()` 或 `do_POST()`。
5. 把捕获到的状态码、响应头和正文重新包装成 FastAPI `Response`。

所以，普通业务并不是 FastAPI 重写，而是被“套壳”后继续运行旧处理器。

## 6. 一次请求的完整路径

以“员工提交请假”为例：

```text
ApplyView.submit()
  -> VP.uploadFiles()
  -> POST /api/upload
  -> POST /api/requests
  -> FastAPI compatibility_route()
  -> run_legacy()
  -> Handler.do_POST()
  -> 校验假种、日期、时限、额度、材料、关联单
  -> INSERT leave_requests
  -> bind_attachments()
  -> notify_approvers()
  -> 返回 JSON
  -> Vue 更新提示并跳转 /records
```

以“审批员批准”为例：

```text
AdminView.doApprove()
  -> POST /api/admin/requests/{id}/action
  -> Handler.do_POST()
  -> require("approver")
  -> 防自审
  -> 校验审批范围
  -> 校验状态
  -> add_approval_balance()
  -> 校验余额
  -> UPDATE leave_requests
  -> INSERT approval_logs
  -> 扣减 leave_balances
  -> notify_user()
  -> 返回 JSON
```

## 7. 数据模型

核心关系：

```text
users
  -> leave_balances
  -> leave_requests
       -> approval_logs
       -> leave_adjustments
            -> adjustment_logs
  -> notifications
  -> sessions
  -> attachments
  -> approval_delegations (approver_id / delegate_approver_id)

calendar_days 独立保存节假日和调休工作日。
```

11 张表的作用：

| 表 | 作用 |
| --- | --- |
| `users` | 账号、密码摘要、角色、工龄、部门、审批关系 |
| `leave_balances` | 每个员工、每种假期的剩余额度 |
| `leave_requests` | 请假主单 |
| `approval_logs` | 每次审批动作和留言 |
| `calendar_days` | 法定节假日、调休工作日 |
| `leave_adjustments` | 提前返岗、销假、续假手续 |
| `adjustment_logs` | 返岗续假的审批动作 |
| `attachments` | 证明材料元数据，关联用户与业务实体 |
| `notifications` | 站内消息 |
| `sessions` | 数据库持久化登录会话 |
| `approval_delegations` | 审批代理关系 |

`attachments` 使用多态关联：`entity_type` 加 `entity_id`，目前可取 `pending`、`request`、`adjustment`。

## 8. 角色与审批范围

数据库角色只有两种：

- `employee`
- `approver`

审批范围不是简单的“所有审批员都能看所有申请”。当前规则是：

1. 员工通过 `approval_approver_id` 指定直属审批员。
2. 审批员只能查询 `approval_approver_id` 等于自己的员工。
3. 有效代理会把自己的审批范围扩展到被代理审批员的员工。
4. `all=1` 的历史查询不做范围过滤，但仍要求审批员角色。
5. 员工不能审批自己的申请。

## 9. 当前系统的主要接线问题

### 已加载但后端缺失

`pages-employee.js` 中仍有以下调用：

```text
/api/requests/{id}/keep
/api/requests/{id}/archive
/api/requests/trash
/api/requests/{id}/cancel
```

当前 `server.py` 没有这些路由。它们对应的归档、垃圾桶、取消功能不可用。

同时，已加载页面读取了一些后端不会返回的字段：

```text
calc.balance
calc.leave_length
approval_steps
current_approver_name
is_final_step
acting_for_name
proxy_actor_name
```

这些字段默认为空或 `undefined`，相关 UI 不会完整工作。

### 未加载的完整模块

以下文件有大量页面、接口调用和 UI 设计，但脚本未加载且后端也没有对应路由或数据表：

```text
pages-attendance.js
pages-overtime.js
pages-stats.js
pages-employee-admin.js
```

判断一个功能是否真实可用，必须同时满足：

```text
脚本已加载
组件已注册
路由可进入
按钮/表单已接线
API 路由存在
数据表存在
权限校验存在
```

## 10. 安全与运行风险

1. `ai_config.json` 内含真实 API Key，且 `.gitignore` 没有排除它。应立即轮换密钥，并改为环境变量。
2. 任何已登录账号都能调用 `POST /api/ai/config`，当前没有管理员限制。普通员工可修改全局 AI 配置。
3. `run.bat` 指向项目外虚拟环境，移动项目后可能无法启动。
4. 项目目录没有 Git 元数据，无法通过版本历史判断哪些代码是实验性残留。
5. 当前是局域网原型，不能直接作为公网生产系统部署。
